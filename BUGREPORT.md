## BR-02. NaN и бесконечности в числовых аргументах

**Тип:** неоднозначность. **Источник:** SPEC 5, 6.2, 6.5–6.6;
REVIEW_Kharchenko.md, пункт 1.

`float()` принимает `nan`, `inf` и соответствующие строки. Для бесконечной
длительности условие `duration_min > 0` формально выполнено; неясно, должна ли
операция отклоняться или запускать посадку. Точных сообщений для этих значений нет.

**Запрос автору:** явно определить допустимость специальных чисел и сообщения.
**Временное решение:** все числовые аргументы должны быть конечными. Для
нагрузки, топлива и мощности специальные числа не проходят заданные диапазоны.
Для длительности дополнительно проверяется конечность. Возникает `ValueError`
с существующим сообщением соответствующего параметра: `payload_kg вне допустимого
диапазона`, `fuel_l вне допустимого диапазона`, `duration_min должен быть
положительным` или `power_usage должен быть в диапазоне (0, 1]`.
Состояние при ошибке не меняется. При бесконечной скорости, внедрённой во
внутреннее поле, возникает `InvalidState("нарушен инвариант режима")`.

## BR-03. Итоговая скорость при переходе в flight

**Тип:** противоречие. **Источник:** SPEC 3.1 и таблица 3.2;
REVIEW_Kharchenko.md, пункт 3.

Раздел 3.1 требует сохранять заранее заданную скорость, таблица 3.2 указывает
`MIN_FLIGHT_SPEED_KMH`. Для входа 100 км/ч результаты различаются.

**Запрос автору:** подтвердить сохранение входной скорости и согласовать таблицу.
**Временное решение:** согласно явному правилу 3.1 и пояснению после таблицы
переход скорость не создаёт и не увеличивает; входные 100 км/ч сохраняются.
Переходы из flight в hover/road устанавливают 0 по таблице.

## BR-04. Способ подготовки скорости вне публичного API

**Тип:** противоречие интерфейса. **Источник:** SPEC 2.1–2.2, 3.1, 6.4;
tests/base.py, `setSpeed()` и `force_state()`.

Все поля объявлены доступными только для чтения и сеттер скорости запрещён.
При этом SPEC 2.1 приводит пример `self.speed_kmh = new_value`, который
несовместим со свойством без сеттера. Из начального road перейти в flight,
используя только публичные команды, невозможно: никто не создаёт скорость 80.

**Запрос автору:** описать границу внешнего расчётного модуля и согласованный
способ передачи рассчитанной скорости; исправить пример присваивания.
**Временное решение:** публичное свойство остаётся без сеттера. Скорость хранится
в `_speed_kmh`, совместимо с авторской фикстурой. README показывает подготовку
Given тем же способом с явной пометкой о внутреннем поле. Публичные методы
не разгоняют транспорт и не расширяют API.

## BR-05. Отсутствует таблица устойчивых режимов

**Тип:** неполнота ТЗ. **Источник:** SPEC 2.3, 6.6;
CHANGELOG.md, запись MR #1 (`9fe3459`).

SPEC 2.3 требует соответствовать строке таблицы, а 6.6 ссылается на таблицу 2.3,
но в текущем файле таблицы нет. В CHANGELOG указано её удаление.

**Запрос автору:** восстановить единую непротиворечивую таблицу либо заменить
ссылки полным текстовым определением.
**Временное решение:** конфигурации взяты из начального состояния, следствий
2.3, шагов 3.2 и неизменённых проверок tests/base.py:

| Режим | На земле | В воздухе | Роторы | Крылья | Скорость |
|---|---|---|---|---|---|
| road | да | нет | сложены | сложены | 0 |
| hover | нет | да | раскрыты | сложены | 0 |
| flight | нет | да | сложены | раскрыты | ≥ 80 |

Для запрошенного перехода в flight допускается заранее подготовленная скорость
при сохранении исходной конфигурации road/hover, как предписывает SPEC 2.3.

## BR-07. Не покрыт расход всего резерва при аварийной посадке

**Тип:** пробел тестового покрытия. **Источник:** SPEC 3.3, 7;
M-11, M-15, M-19; REVIEW_Kharchenko.md, пункт 5.

**Запрос автору:** проверить последовательность `LegoVehicle(0, 6)`, подготовка
скорости 80, переход в flight, `move(1, 1)`. Ожидаются 0 л, устойчивый road
и полный маршрут `("flight", "hover", "road")` без исключения.
**Действие D:** весь аварийный маршрут проверяется до изменения состояния;
его промежуточная воздушная ступень может расходовать резерв. Вызов обычного
`transition()` для flight → hover здесь непригоден: он потребовал бы сохранить
4 л уже после первой ступени. Случай отдельно проверен, тесты автора не менялись.

## BR-09. Авария при искусственно повреждённом запасе топлива

**Тип:** неописанный защитный случай. **Источник:** SPEC 3.3, 6.5–6.6;
tests/base.py, `force_state()`.

Публичные операции сохраняют воздушный резерв 4 л. Но тестовая фикстура может
создать hover с менее чем 2 л или flight с менее чем 4 л. Требование посадки
«без исключения» тогда несовместимо с неотрицательным топливом и ценой маршрута.

**Запрос автору:** явно ограничить правило гарантированной автопосадки
достижимыми состояниями либо определить ошибку для повреждённого запаса.
**Временное решение:** `NotEnoughFuel("недостаточно топлива для посадки")`
без изменения состояния, если весь маршрут оплатить нельзя. Для состояний,
достижимых публичными командами, эта ветка не требуется.
